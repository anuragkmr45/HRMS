# Regularization and Manager Queue UX Gap Closure Plan

Task: `GEO-S10-015`
Status: Implementation plan pending v2 regularization APIs
Owner: Pratik
Last updated: 2026-07-20

## Objective

Complete the employee attendance correction and manager review experience without editing original attendance evidence. Employees submit a correction request; authorized approvers append approve, return, or reject actions; the backend rebuilds the daily projection from immutable events and actions.

## Current Gaps

- The employee dashboard links to `/attendance` but no regularization form exists.
- Query and mutation hooks exist for employee history and manager queue, but no dedicated employee or manager screen consumes them.
- `/attendance/exceptions` is limited to HR/Admin in the client even though the backend supports manager-scoped decisions.
- The exceptions table combines automatic exceptions and correction requests.
- Approve/reject is executed from an icon-only row without a detail review.
- Reject remarks are generated by the client instead of collected from the approver.
- The UI does not show original punches, requested changes, policy context, evidence state, or immutable action history.

## Route and Navigation Plan

Employee routes:

- `/attendance/regularizations`: request list and status history.
- `/attendance/regularizations/new`: correction form.
- `/attendance/regularizations/$id`: employee-visible request detail.

Manager/HR routes:

- `/attendance/review`: scoped review queue.
- `/attendance/review/$id`: request/evidence detail and decision form.

HR/Admin monitoring remains available under `/attendance/exceptions`, but regularization decisions link to the review detail instead of executing from the exception row.

Navigation visibility is a convenience. Backend object authorization remains mandatory for every list, detail, evidence, and decision request.

## Employee Request Flow

### Entry points

- Selected day in employee calendar.
- Missing-punch/exception message.
- Attendance page quick action.
- Existing returned request.

Entry points pass only a date/request identifier. The form reloads authoritative day and policy context.

### Form structure

1. `Attendance date`
   - Date picker bounded by policy request window and period locks.
   - Defaults from selected calendar day.
2. `What needs correction?`
   - Missing check-in.
   - Missing check-out.
   - Incorrect time.
   - Missing/incorrect break.
   - Work mode correction.
   - Other attendance correction.
3. `Recorded attendance`
   - Read-only original event timeline.
   - Suppressed/replaced events remain visible as original evidence where authorized.
4. `Requested correction`
   - Ordered event editor using date/time inputs and event-type menus.
   - Prevent duplicate event types/timestamps and invalid local order before submission.
5. `Reason`
   - Required, 10-1000 characters.
   - No sensitive-location prompt in free-form copy.
6. `Supporting documents`
   - Optional document IDs through the Documents module when policy permits.
   - No direct file metadata or object-storage URL in the regularization body.
7. `Review`
   - Before/after timeline, approver route, policy notice, and acknowledgement.

The client provides basic time-order feedback, but the backend resolves shift date, policy, overlap, period lock, and valid state transitions.

### Submission

- Use a stable idempotency key and client event ID.
- Return `201` for first creation and treat replay as success.
- Navigate to request detail after success.
- Invalidate employee day, calendar, exception, context, and regularization queries.
- Do not modify the displayed original events optimistically.

## Employee Request States

| Status | Employee actions | Copy intent |
| --- | --- | --- |
| Draft (client only) | Edit, discard, submit | Not sent to approver |
| Pending | View, withdraw if policy allows | Awaiting named role/approver |
| Returned | Edit correction and resubmit | Address approver remarks |
| Approved | View result and action history | Daily projection updated |
| Rejected | View reason; create a new request if allowed | No original evidence changed |
| Withdrawn | View history | Request closed by employee |
| Superseded | View replacement link | Replaced by later correction |

Server status values are normalized centrally. Unknown values render read-only with a refresh action.

## Manager Review Queue

### Queue layout

Use a work-focused table/list, not exception-type tabs. Filters:

- Pending/returned/escalated status.
- Employee.
- Date range.
- Department/team.
- Correction type.
- Evidence state.
- Policy reason code.
- Age/SLA.

Columns:

- Employee and employee code.
- Attendance date and shift.
- Correction summary.
- Evidence/exception status.
- Submitted age.
- Current approver.
- Status.
- One `Review` command.

Queue counts come from the backend. The client does not calculate authorization or queue ownership.

### Detail review

The detail screen has four un-nested sections:

1. Employee/day context: employee, date, shift, work mode, policy version.
2. Before/after timeline: immutable recorded events versus requested correction.
3. Evidence and reasons: decision reason codes, permitted evidence summary, documents, and restricted-location indicator.
4. Action history: submission, returns, resubmissions, decisions, actor, time, and remarks.

Exact coordinates are hidden by default. When a separately authorized evidence endpoint exists, show a deliberate `View restricted location evidence` command with audit notice; do not preload the data.

## Decision UX

Decision commands are `Approve`, `Return`, and `Reject`.

- Approve opens a review dialog with optional remarks unless policy requires a reason.
- Return requires actionable remarks and keeps the request editable/resubmittable.
- Reject requires a reason code and remarks.
- Every dialog shows employee/date, requested change summary, current version, and downstream effect.
- Self-approval is blocked by the backend and not presented as an enabled command.
- A stale version conflict closes the dialog, refreshes detail/history, and requires a new decision.
- One decision gets one idempotency key.
- Success navigates to the next queue item only after the result and refreshed queue confirm it.

The client never generates fake reject remarks.

## Decision and Evidence Data Requirements

Queue item:

```ts
interface RegularizationQueueItem {
  id: string;
  version: number;
  employee: { id: string; employeeCode: string; name: string };
  attendanceDate: string;
  shiftLabel: string | null;
  correctionType: string;
  changeSummary: string;
  evidenceState: string;
  reasonCodes: string[];
  status: string;
  currentApprover: { id: string; name: string } | null;
  submittedAt: string;
  canDecide: boolean;
}
```

Detail additionally requires:

- Original immutable events.
- Requested event/correction items.
- Current day projection.
- Policy/shift version references.
- Evidence summary and restricted evidence capability.
- Supporting document summaries.
- Ordered immutable actions.
- Allowed decisions with reason requirements.

No general response includes exact coordinates or geofence geometry.

## Automatic Exceptions versus Regularizations

Automatic exceptions and employee correction requests remain distinct:

- Exception: a reason-coded projection/review condition such as late, missing punch, boundary uncertainty, or poor accuracy.
- Regularization: an employee-requested historical correction workflow.

An exception may link to a regularization, but approving an exception row directly is not allowed. The review screen must show which object is being decided.

## Error and Empty States

- No eligible days: explain policy request window and period locks.
- Duplicate pending request: link to existing request.
- Period locked: read-only day with payroll/HR guidance.
- Invalid event order: inline field errors plus summary.
- Not current approver: refresh queue and show read-only detail if authorized.
- OCC conflict: refresh detail and action history.
- Missing/removed evidence: show reason code; do not fabricate availability.
- No queue items: compact completion state with filters reset command.
- Network uncertainty after submission/decision: retry with the same idempotency key.

## Authorization Matrix

| Capability | Employee | Manager | HR/Admin | Auditor |
| --- | --- | --- | --- | --- |
| Create own request | Policy controlled | Own request only | Own request only | No |
| View own requests | Yes | Yes | Yes | Scoped read only |
| View team queue | No | Reporting/assigned scope | Company scope | Scoped read only |
| Decide request | No self-decision | Assigned scope | Configured fallback scope | No |
| View evidence summary | Own | Scoped | Scoped | Scoped read only |
| View exact location | Own policy-dependent | Separate permission | Separate permission | Separate audited permission |

The table describes intended UX. Backend policy is authoritative.

## Accessibility and Responsive Behavior

- Timelines use semantic ordered lists with text labels.
- Before/after differences do not rely on color alone.
- Decision dialogs require explicit button labels and maintain focus.
- Table rows become labeled review items on narrow viewports.
- Filters remain accessible through a sheet/drawer on mobile.
- Long remarks wrap and remain selectable.
- Exact timestamps include accessible timezone text.

## Test Matrix

Employee:

- Missing check-in/out, incorrect time, break, work mode, and other correction.
- Invalid ordering, duplicate pending request, request-window expiry, and locked period.
- Timeout/replay, returned resubmission, approval, rejection, and withdrawal.

Manager/HR:

- Assigned manager queue, hierarchy boundary, backup/fallback approver, and self-decision block.
- Approve, return, reject, required remarks, stale version, and repeated decision replay.
- Automatic exception without request cannot be decided as a regularization.
- Exact evidence is not fetched without explicit permission/action.

E2E:

- Calendar day to employee request to manager approval to updated employee day.
- Returned request edit and resubmit.
- Cross-company/request-ID negative access.
- Desktop and mobile review flows with keyboard-only decisions.

## Acceptance Criteria

- Employees can create and track regularization requests from an authoritative day context.
- Managers have a dedicated scoped queue and detail review screen.
- Approval reason, original evidence, requested changes, and immutable action history are visible as permitted.
- Return/reject collect real remarks; no generated decision text remains.
- Automatic exceptions and correction requests are not conflated.
- Decisions use OCC and idempotency, block self-processing, and refresh after conflicts.
- Exact location evidence remains restricted and lazy-loaded.
- Routes, data requirements, states, authorization, accessibility, implementation sequence, and tests are defined.
